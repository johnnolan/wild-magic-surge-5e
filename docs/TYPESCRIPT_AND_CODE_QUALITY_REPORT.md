# TypeScript and Code Quality Report

## Summary

The project has a good starting point: it uses TypeScript, enables `strict`, and includes Foundry API declarations in the compiler configuration. At present, though, TypeScript is not acting as a reliable quality gate. The configured source include is misspelled, there is no type-check script, several Foundry and D&D5E boundaries are weakly typed, and a direct compiler run currently reports 152 errors.

This report is based on the repository state and the [Foundry API documentation](https://foundryvtt.com/api/), which currently documents V14.368.

## TypeScript Setup and Findings

- **Type checking is not part of the normal workflow.** [`package.json`](../package.json) has build, test, and lint scripts, but no `typecheck` script. The build uses esbuild, which transpiles TypeScript without performing TypeScript's semantic checks. Running `npx tsc --noEmit --pretty false` directly currently exits with 152 errors across production code, tests, and mock data.
- **The configured include is misspelled.** [`tsconfig.json`](../tsconfig.json) uses `"includes"`; TypeScript's option is `"include"`. The invalid key is ignored, so TypeScript falls back to its default project-file discovery. Tests and mock files are consequently included along with production source. Correct the key and use a separate test config if test fixtures need different typing rules.
- **`strict` is enabled, which is valuable.** Keep it. The current diagnostics expose real edge cases such as nullable Actor IDs, optional canvas tokens, an `unknown` socket payload being read without narrowing, and a reference to an undefined `roll` in `scripts/module.ts`.
- **The target and module settings should be intentional.** TypeScript targets ES2020/CommonJS while esbuild bundles to ES6. Choose settings based on the Foundry browser runtime and the actual bundler/test pipeline; for a no-emit type-check config, align module resolution with the bundler and the V14 type package guidance rather than using these settings by default.
- **The wildcard path mapping is unusually broad.** `"*": ["./scripts/types/*.d.ts"]` can affect resolution of unrelated imports and appears unnecessary for the current relative imports. Remove it unless a specific alias depends on it; use narrow aliases when needed.
- **`skipLibCheck` is enabled.** This can be a practical way to avoid checking third-party declaration internals, but it does not suppress errors in this project. Do not use it as a substitute for resolving errors in application code.

## Foundry Types and Imports

- **The declarations are community-maintained, not official Foundry-authored types.** [`@league-of-foundry-developers/foundry-vtt-types`](https://github.com/League-of-Foundry-Developers/foundry-vtt-types) describes itself as unofficial type definitions. Foundry's [API documentation](https://foundryvtt.com/api/) is the official reference for API support and public/private boundaries; the types package provides compile-time assistance and can lag or disagree with runtime behavior.
- **The GitHub release page is stale, but the project is active.** Checked 2026-10-01: GitHub's tagged Releases still show V13-era releases, but `main` has recent V14 type changes and npm publishes V14 beta snapshots. npm dist-tags are split: `latest` is still `13.346.0-beta.20250812191140`, while `beta` points to `14.366.0-beta.20261001000223` and `prerelease` to an older V14.366 snapshot. The repository's default README still has stale V13 beta wording, so use npm metadata and recent commits, not the README/release badge alone, to determine current availability.
- **Match declaration and runtime versions.** [`package.json`](../package.json) pins a V13.346 beta declaration while the module manifest targets V14.367. For V14 development, explicitly opt into the V14 beta channel, then pin the resolved version for reproducible builds. The newest snapshot found here is based on 14.366, two Foundry patch builds behind the current 14.368 runtime, so validate the declarations against the APIs this module actually uses; do not assume `latest` or the beta's patch number matches the running Foundry version.
- [ ] **Add the selected V14 snapshot as a dev dependency.** Install and validate [`14.366.0-beta.20261001000223`](https://www.npmjs.com/package/@league-of-foundry-developers/foundry-vtt-types/v/14.366.0-beta.20261001000223) with `npm install --save-dev @league-of-foundry-developers/foundry-vtt-types@14.366.0-beta.20261001000223`. This exact install command is for the V14 migration branch; only commit the resulting dependency and lockfile changes after reviewing them and validating against the Foundry runtime you intend to support.
- **No maintained successor surfaced in this check.** npm search returned the scoped package and an unscoped `fvtt-types` alias with the same description/version lineage, not a newer independent core-API declaration set. A package named `@revolutionarygamesco/common-foundryvtt` is a project-specific helper library, not a replacement. Treat the League package as the current practical option, while keeping local augmentations small and checking Foundry's official API docs for public API status.
- **Avoid importing declarations through package internals.** [`scripts/module.ts`](../scripts/module.ts) imports `RoundData` from a deep `src/foundry/client/...` path; the current compiler cannot resolve it. Prefer a public package export, a type inferred from the documented hook callback, or a small local type when the upstream type is not public. Mark type-only dependencies with `import type` so they cannot become runtime imports.
- **Most Foundry globals should come from the configured global declarations.** `game`, `Hooks`, `Actor`, `Item`, `Roll`, and other Foundry globals are supplied by the declarations package; they should not need hand-written runtime imports. Keep local ambient declarations focused on module-owned types and supported augmentations, rather than weakening Foundry globals.
- **Core Foundry types do not fully describe D&D5E system data.** Errors around `actor.system.resources`, `actor.system.details.level`, Item types, and spell fields show the gap between core document types and system-specific data. Add compatible D&D5E declarations where available, or define narrow module-owned interfaces/guards for the fields this module reads. Do not cast all of `actor.system` to `any`.
- **Use public APIs, not just APIs that happen to type-check.** The Foundry documentation distinguishes public APIs from private/internal APIs. Check the documentation's annotations before relying on underscored members or implementation-only properties; types may expose members that Foundry does not promise to preserve.

## V14 Package-Specific Type Additions

The V14.366 snapshot exposes a public `configuration` subpath with the `Hooks.HookConfig` registry. The following module-owned types would make the highest-risk integration points substantially safer:

- [ ] **Augment the custom Hook registry.** Add entries for the module's published events (`manualTriggerWMS`, `reset`, `Reset`, `ResetDieDescending`, `ResetIncrementalCheck`, `SetDieDescending`, `SetIncrementalCheck`) and emitted notifications (`CheckForSurge`, `IsWildMagicSurge`, `DieDescendingChanged`, `IncrementalCheckChanged`). Model each callback's actual arguments, including payload objects, so both `Hooks.on` listeners and `Hooks.callAll` calls are checked. The augmentation target is the package's public `@league-of-foundry-developers/foundry-vtt-types/configuration` export; do not augment a deep `src/` path.
- [ ] **Define a validated socket message union.** Replace `unknown` property access and ad hoc object literals for `module.wild-magic-surge-5e` with a union discriminated by `event` (currently `SurgeCheck`). Validate the incoming value at runtime before narrowing it; type declarations alone do not validate socket data.
- [ ] **Use the real Combat hook contract.** Remove the deep `RoundData` import from `scripts/module.ts` and let `Hooks.on("updateCombat", ...)` infer the V14 callback arguments, or annotate them from the package's public hook signature. The first argument is a Combat document, not a custom `RoundData` type; rename it to `combat` and access `combat.combatant?.actor` after narrowing.
- [ ] **Type the D&D5E Activity integration separately from core Foundry.** The D&D5E `dnd5e.postUseActivity` event passes an Activity as its first argument, then usage configuration and results. The current callback annotates that value as a core `Item` and then assumes both `activity.item` and `activity.consumption`. Use a D&D5E declaration if available for the installed system release; otherwise define a small module-owned consumer interface for `item`, `item.actor`, and `consumption.spellSlot`, and verify it against that release's hook implementation. See the [D&D5E activity hook source](https://github.com/foundryvtt/dnd5e/blob/6.0.x/module/documents/activity/mixin.mjs).
- [ ] **Represent the system data this module reads.** Define narrow D&D5E-facing shapes for spell Item `system.level`, Actor `system.details.level`, Actor `system.resources` slots, and the Item/Actor subtype values used by the feature checks. Prefer the system's exported declarations if the supported system version provides them; otherwise centralize structural interfaces and type guards rather than casting `system` to `any` in each consumer.
- [ ] **Type module-owned flags and settings.** Add a key-to-value map for the `wild-magic-surge-5e` Actor flags and a setting-key/value map for the module's settings. Use typed accessors around `getFlag`/`setFlag` and `game.settings.get`/`set` so misspelled keys and wrong value types are caught at one boundary.
- [ ] **Type the chat and sheet hook callbacks.** V14 declarations distinguish the legacy `renderChatMessage` arguments from `renderChatMessageHTML`'s HTMLElement-based callback. Select the hook used by the implementation and use its declared message/context types. Replace the header-controls `Array<any>` with the callback's declared control entry type.
- [ ] **Move application-owned aliases out of globals.** Types such as `SurgeType`, `Comparison`, `DieValue`, `HookValue`, `ResourceValue`, and `SpellLevelFormula` currently live in `scripts/types/globals.d.ts`. Export module-owned types from a domain/types module and import them where used; keep ambient declarations for Foundry module augmentations only.

For V14's package subpath exports to resolve correctly, set TypeScript's module resolution to a mode compatible with package `exports` (the package README recommends `bundler`) in the dedicated type-check configuration. Keep that setting aligned with the actual compiler and esbuild pipeline.

## Concrete Type and Runtime Risks

- [`scripts/module.ts`](../scripts/module.ts): the `wild-magic-surge-5e.reset` callback passes `roll`, but that name is not defined in the callback or module scope. Invoking this hook can throw a `ReferenceError`; correct the intended reset behavior rather than suppressing the diagnostic.
- [`scripts/module.ts`](../scripts/module.ts): socket payloads are typed as `unknown` but read as though they always have `event` and `data`. Define a discriminated payload union and validate/narrow incoming socket data before use. Custom module hooks should also be added to the hook typings so callback arguments are checked.
- [`scripts/module.ts`](../scripts/module.ts) and [`scripts/TriggerMacro.ts`](../scripts/TriggerMacro.ts): actor IDs and canvas tokens can be absent or nullable, but downstream calls and annotations often assume they are present. Guard these values or reflect the optionality in the function contracts.
- [`scripts/panels/Helpers.ts`](../scripts/panels/Helpers.ts): settings helpers use `any` for their inputs, output collections, and `game.settings` access. Replace these with a settings-key union, typed setting metadata/value records, and a typed form-data shape. Keep any unavoidable cast at one documented adapter boundary.
- [`scripts/module.ts`](../scripts/module.ts): the header control callback uses `Array<any>`; use the Foundry header-control entry type from the matching declarations package.
- [`scripts/utils/Resource.ts`](../scripts/utils/Resource.ts): `SetResource` mutates `this.defaultValue` directly, so resource writes can change the shared static default object. Create a fresh object for each update and avoid returning shared mutable defaults.
- [`scripts/Chat.ts`](../scripts/Chat.ts): `ChatMessage.create` is called without `await` inside an async method, so asynchronous create failures are not propagated to callers. Await it and type the input as create data rather than as an already-instantiated `ChatMessage` document.
- The many `global as any` casts in tests make fixtures easy to write but erase checks at the test boundary. Prefer shared typed Foundry/Jest setup helpers and small fixture builders; use `Partial<T>` only for intentionally incomplete fixtures, then cast in one explicit helper if the API requires a complete document instance.

## Recommended TypeScript Workflow

1. Fix `include`, then create a production type-check config that only covers shipped TypeScript and a separate test config that includes tests, `MockData`, and `__mocks__`.
2. Add `"typecheck": "tsc --noEmit"` and run it in CI alongside tests, build, and lint. Treat newly introduced errors as failures; resolve existing errors in batches by production module first, then test fixtures.
3. Update Foundry declarations to the V14 target before fixing API-specific errors. Use Foundry's documented hook signatures and public exports, and add typed hook augmentations for module-owned events and D&D5E events not described by the core package.
4. Replace production `any` usages with specific types, `unknown` plus runtime narrowing, or generics. Remove stale `@ts-expect-error` comments after the underlying mismatch is fixed; the current compiler reports several as unused.
5. Keep runtime/build settings and type-check settings explicit. The compiler should check source; esbuild should bundle it; Jest should test it. Avoid making one configuration accidentally include every category of file.

## Other Best Practices

- **Lint the whole production surface.** [`.eslintrc.json`](../.eslintrc.json) ignores `scripts/panels/**/*.ts`, including all five legacy settings panels. Remove that ignore or add a deliberate replacement lint rule set so these files receive the same checks as other production code.
- **Make async work observable.** Await document creation, actor updates, flag writes, and nested helper calls when their completion matters. This makes failures visible and avoids tests passing before persistence has finished.
- **Use immutable defaults and explicit return contracts.** Clone default records before mutation, annotate exported helper return types, and use `readonly` for configuration data that should not change.
- **Reduce repeated settings-panel code.** The five legacy panels share settings-list and update behavior. After migration to ApplicationV2, consolidate genuinely shared rendering/submission behavior into a base/helper pattern, while keeping each panel's setting list explicit.
- **Keep naming and formatting consistent.** Static method names currently use PascalCase while other methods use camelCase, and some panels differ in formatting. Choose one convention, rely on the existing Prettier-backed lint rule, and format as part of the same focused changes rather than doing unrelated churn.
- **Test the boundary that the unit suite cannot model.** Jest mocks can validate decisions, but they do not prove Foundry hook timing, Application rendering, chat visibility, or D&D5E system data shapes. Maintain a short manual smoke-test checklist for those in a real V14 world.
