# Chat message audience and duplicate test plan

This is an implementation checklist for the existing Playwright and Jest suites. Keep the browser cases in plain Given / When / Then language: set a small number of relevant options, cast or click through the real Foundry UI, then inspect the chat seen by each connected user. Build on `e2e/chat.visibility.spec.ts`, `e2e/chat.content.spec.ts`, `e2e/table.spec.ts`, and `scripts/Chat.test.ts`; do not rebuild their fixtures.

## What the reported screenshot shows

The pictured settings are Incremental Check, `whisperToGM=false`, `whisperToGMRollChat=true`, and `enableRollTable=PLAYER_TRIGGER`. The pictured outcome says **No wild magic surge**. The spell card is dnd5e output. The charge-count card is a separate, expected Incremental Check notification when `incrementalCheckToChat` is enabled. No table result should be drawn for this no-surge outcome.

The bare **Gamemaster 1d20** card appears to come from `roll.toMessage()` in `MagicSurgeCheck.WildMagicSurgeRollCheck()`. The later labelled **Wild Magic Surge Check** card is created for the same roll by `Chat.Send()` in `SurgeWildMagic()`. That explains the extra card in the current code. Its audience may also depend on the GM client's Foundry roll mode; the screenshot alone does not prove which players can see it. The recommended product contract below is **one labelled check card and zero bare duplicate roll cards**. A browser reproduction should establish current visibility before the code is changed.

## Audience contract to test

| Message after one eligible cast | Setting that controls it | Expected audience and count |
| --- | --- | --- |
| Prompt when auto checking is off | `magicSurgeChatMessageEnabled`, `whisperToGM` | One public prompt, one GM-only prompt, or zero when disabled |
| Surge or no-surge check result | Corresponding `autoRollD20Message*Enabled`, `whisperToGM` | Exactly one labelled result in its selected audience, or zero when disabled; zero bare check rolls |
| Incremental charge update | `incrementalCheckToChat`, `whisperToGM` | One message on an increment if enabled; zero if disabled or no increment |
| Automatic table result | `enableRollTable=AUTO`, `whisperToGMRollChat` | One result for a normal-level actor in its selected audience; two distinct draws above level 13 are intentional |
| Player-triggered table result | `enableRollTable=PLAYER_TRIGGER`, `whisperToGMRollChat` | Zero before a click; one result per intended click in its selected audience |

`whisperToGM` controls prompt, check-result, and charge messages. `whisperToGMRollChat` controls table results. A public module check can still be affected by the Foundry client's core roll mode except where `PLAYER_TRIGGER` explicitly chooses public mode in `Chat.Send()`. Set the GM client's core `messageMode` to `public` in baseline cases; test other core modes separately.

The module has **no player-only audience option**. A cast by a player is processed by the GM through the socket, so Foundry's author-only `self` mode would refer to the GM for that check. Do not label a `self`-mode test “player only.” If caster-only check messages are wanted, they require an explicit recipient rule and implementation before an end-to-end test can promise that behavior. The three sessions below can still prove that a public message reaches both players, while a GM-only message reaches neither.

## Shared test structure

- [ ] **CHAT-01 — Observe all participants.** Add a second disposable player session alongside the current GM and caster player. Give only the caster player ownership of the test actor. Use the existing `TestWorld` cleanup and close each player context before deleting its user. Avoid giving the unrelated player actor ownership just to make chat visible.
- [ ] **CHAT-02 — Read chat consistently.** Extend `e2e/support/observations.ts` with a small reader for message ID, author ID, speaker actor ID, content, flavor, roll formula/total, and visible content. Keep `readChatMessages()` as the *actually visible* view. Provide a helper that compares new message IDs across GM, caster, and unrelated player. Foundry may retain private message documents on a player's client with `isContentVisible=false`; the presence of a document alone does not mean its content was seen. Use rendered chat as a spot check for the screenshot case.
- [ ] **CHAT-03 — Count the right cards.** For each cast, snapshot chat IDs before the action and classify only new cards: dnd5e spell card, bare check roll, labelled check result, charge update, table result, and player-trigger button. Use a unique marker in configurable text and a disposable table with a unique name. Never call two cards duplicates solely because they share a roll total. Assert the bare roll count separately from the labelled result count, and identify expected high-level double table draws separately.
- [ ] **CHAT-04 — Wait for completion.** Cast through `castSpellFromSheet()` and wait for the slot change plus the module's `IsWildMagicSurge` hook (or another terminal signal for reminder-only flows). Poll for expected messages to arrive in each session before asserting absence or final counts. Do not add fixed sleeps. Restore settings, core message mode, hook listeners, users, actors, tables, and messages even if a test fails.

## Browser specs to add

Prefer small files grouped by observable behavior. Reuse the existing visibility and content cases instead of copying them. Titles should read like “Given GM-only check messages, when the player casts, only the GM sees the result.”

- [ ] **CHAT-05 — Screenshot regression** (`e2e/chat.duplicates.spec.ts`). Given Incremental Check, `PLAYER_TRIGGER`, `whisperToGM=false`, `whisperToGMRollChat=true`, an enabled charge message, and a guaranteed non-surge result, let the caster player cast Magic Missile. Assert one spell card, one charge update, one labelled no-surge result, zero table results/buttons, and **zero bare GM d20 cards**. Check all three sessions. Before fixing the module, retain the failing reproduction or mark it as an expected failure with a clear issue reference; do not weaken the count. `configureIncrementalIncrease()` can guarantee a non-surge, but its `1d20+20` formula differs from the screenshot. For the exact `1d20` reproduction, seed an Incremental threshold and use the existing deterministic Foundry dice helper on the **GM page**, because the GM executes the socket check. Keep the dice override active until the GM receives the check-result hook and chat card; the sheet action may finish before socket processing does.
- [ ] **CHAT-06 — No duplicate on either outcome** (`e2e/chat.duplicates.spec.ts`). Run one guaranteed Standard surge and one guaranteed Standard no-surge with table mode `DEFAULT` (None). For each, assert one labelled check card, zero bare check cards, and no second copy of the same message ID or text. Repeat one case with the corresponding result-message switch off: the outcome flag still changes, while no check card or bare roll is posted. Add a focused Jest assertion that `WildMagicSurgeRollCheck()` evaluates and returns a roll without posting it; `Chat.Send()` should own the single result message.
- [ ] **CHAT-07 — Prompts, results, and charges** (`e2e/chat.visibility.spec.ts`). Expand the existing public/GM-only tests to use three sessions. For each distinct message type, verify public means GM + caster + unrelated player each see one card, while GM-only means only GM sees its content. Assert the opposite audience sees zero. Cover the enabled/disabled charge switch in `chat.content.spec.ts`; on a threshold reset, do not expect a charge-increase card.
- [ ] **CHAT-08 — Independent table settings** (`e2e/chat.table-audience.spec.ts`). With a guaranteed surge and `AUTO`, run the four meaningful pairs of `whisperToGM` and `whisperToGMRollChat`: public/public, GM/public, public/GM, GM/GM. For each pair, assert exactly one labelled surge check and one table result for a normal-level caster; assert their audiences independently in all three sessions. Reuse the table fixture. Keep the existing above-level-13 two-draw test as an explicit exception to the one-result count.
- [ ] **CHAT-09 — Player-triggered table** (`e2e/chat.table-audience.spec.ts`). Given `PLAYER_TRIGGER`, confirm the surge check and button are visible to the player when `whisperToGM=false`, and no table result exists before the click. Click once as the caster player; assert exactly one result and the audience selected by `whisperToGMRollChat`. Repeat with table whisper on. With `whisperToGM=true`, verify the player cannot see/use the button and no table result is created. Check the unrelated player as well. If a player-triggered table draw runs as the clicking player, confirm the whisper option still protects the result in that path.
- [ ] **CHAT-10 — Core roll modes and actor ownership** (`e2e/chat.core-mode.spec.ts`). With module whispers off, compare Foundry core `public` with one nonpublic mode on the GM client to establish how a plain roll and a module check are routed. Then prove `whisperToGM=true` wins over a public core mode. Include one `PLAYER_TRIGGER` case to verify that its check/button stays public as coded. State the actual behavior of core `self` mode in the test name; it is not a module player-only feature. The unrelated player makes ownership leaks observable.
- [ ] **CHAT-11 — Special paths** (`e2e/chat.duplicates.spec.ts` or the owning spec). A spent Tides of Chaos use causes an automatic surge without `WildMagicSurgeRollCheck()`, so expect no check d20 card; count its configured message and table action once. For Path of Wild Magic, expect a prompt/button or automatic table result as configured, but no sorcerer check roll. Keep one representative case per path, referencing `e2e/tides.spec.ts` and `e2e/barbarian.spec.ts`.

## Unit coverage and completion

- [ ] **CHAT-12 — Keep routing rules cheap to check** (`scripts/Chat.test.ts`, `scripts/MagicSurgeCheck.test.ts`). Use table-driven Jest cases for `DEFAULT`, `ROLL`, and `TABLE` with each relevant whisper flag, the core roll mode, `PLAYER_TRIGGER`, missing roll/table inputs, and message creation called exactly once. Verify which option is passed to `ChatMessage.create()`. Keep real cross-user visibility assertions in Playwright, not mocks.
- [ ] **CHAT-13 — Run and report.** Run each changed browser spec alone, then the chat group, then the full E2E suite twice, plus Jest, `yarn typecheck:e2e`, and `yarn lint:check`. Report the exact Foundry/dnd5e pair. A passing regression must show the screenshot case creates one labelled check result and no bare roll, and that no player receives content intended only for the GM.

Implementation order: observation helpers → screenshot reproduction → single-card product fix and Jest guard → three-user audience matrix → table/button matrix → special paths and full verification. Keep any product fix in a separate commit from the test framework where practical.
